# Data Lifecycle Checklist (Generation 2 export / delete / retention / privacy)

> Status: **current source with Unreleased rc.5 changes** — this checklist describes the
> release's export, deletion, retention, and privacy boundary. Source publication does
> not itself upgrade an instance; deployment status is specific to each operator.
>
> Canonical DDL: `internal/db/generation_two.sql`, embedded by `internal/db/schema.go`, plus registered extension schemas; manifest: `internal/db/schema_manifest.go`;
> target fingerprint: the build’s canonical `GenerationTwoSchemaHash` and complete manifest.

The table cells below describe the version contract for each exact Generation 2 table
family. The registered routes, export builder, deletion coordinator, retention workers,
and bilingual privacy text are covered by their implementation and contract tests.
Schema presence alone never creates a route or expands a response.

Current account export schema 12 retains earlier safe projections and adds the bounded families below. Its filename is `nonbiriapi-account-export-v12.json`; SQLite `user_version` remains 2. The schema-11 rows remain historical coverage for fields still retained. This does not assert that any particular instance has been upgraded.

Donated keys include the current U128 failure-disable threshold in owner, management and safe export projections. It follows the parent key/donation lifecycle and adds no retention window. Policy edits add no-secret donation review facts, retained under the existing donation-review policy; account deletion removes actor links. A zero threshold preserves error counting but never disables a key for errors. Expiry, withdrawal, bans, manual switches and quota limits remain effective.

Gateway v3 adds a default-off site setting for cost attribution. The optional pseudonym is computed per user and final gateway origin from the deployment key and is never stored as a new identity table, exported, or shown in diagnostics. Debug records only whether it was sent. The receiving gateway can link requests in that scope; ordinary request content and provider retention retain their existing boundaries. The schema expansion preserves existing credentials, counters, generations, error-disablement and configured legal overrides.

The signed-in credit history is a read-only projection of the current user's wallet
entries. It adds no stored data or retention period. Request links use the existing
owner-scoped 30-day log window; expired logs disappear from those links while wallet
history remains available. Donation rewards never expose another caller's request ID.

Authenticated pre-handler rejections and short charity rejections use the same 30-day owner-scoped request-log policy. Pre-handler rows identify the phase and safe rejection stage/reason, with no attempts, usage or call fee; an independently authorized penalty has its own ledger entry. Durable violation windows contain bounded event times, kinds and request references, survive restart without repeating an already executed measure, and are pruned by logical window expiry. They contain no request bodies and are excluded from export. Account deletion clears both durable and cached state.

Every user-associated table or column MUST be checked in the same task that introduces
it. This includes direct `users(id)` links, transitive foreign keys, and no-FK user
references used for late-callback suppression.

`dispatch_response_starts` contains only a claim reference and server timestamp indicating validated charity output. It stores no content, usage, credentials or independent user identity. It is internal settlement/recovery evidence and is excluded from account export; the existing consumer aggregate and credit ledger contain the safe economic result. It follows the parent claim's retention and cascades on claim deletion. Account deletion uses the existing deidentified claim handoff, so late completion can settle accepted work without recreating the user or private data. This adds no public request details or retention period.

`endpoint_key_limits` stores only owner-selected concurrency and RPM values. The owner resource export includes both; the endpoint-key foreign key cascades their deletion with the key/account. They have the same lifetime as the resource. Administrator/steward views disclose only the limits on resources already authorized for those views and cannot edit them. Deleted donation source keys show no current configuration. Admission reuses existing dispatch metadata and adds no counters, request content, retention period or late-writing worker. Recovery and request/account deletion continue through the existing claim state machine; in-flight donor keys and their secret retention rules are unchanged.

General, game, draft-paper and brush accounts are conserved independently. General/game balances may be signed; activity currencies are whole units and never become game-payment funds. `credit_entries.asset_type` survives account-reference removal. Export v10 includes the requester's safe balances, payment splits, activity exchanges and original-asset history. Deletion releases pending capacity and clears all four user wallets atomically against their own asset's external account. General-only charity fees may exceed the admitted reserve when actual usage is known; settled historical charges are never repriced. Administrator user adjustments remain restricted to the existing general/game or cumulative-donation targets.

`game_checkins` stores the independent daily game award and follows the account's lifetime, export and cascade deletion. `game_onboarding_completions` stores game/task key, award, operation and completion time; each of 22 tasks is unique per account, survives 30-day game cleanup and is exported/deleted with that account. `game_onboarding_holds` reserves reward capacity until the parent game's terminal transaction releases it; it cannot silently cascade and lose capacity. Export v10 includes only each hold's ID, game/task key and creation time, excluding internal amounts and parent references.

Saved game rows include rules version and original payment sources. Fishing adds frozen cut rates and gross/net values; LinkLink adds hint/refresh counters and reads six leaderboards from retained successful version-2 summaries. RPS exports only the viewer's source balances and nullable recorded original buy-in/cash-out fields. Old unrecorded values remain null. These additions inherit their parent retention and synchronous deletion rules. The private stable LinkLink tie key follows account lifetime and is never exported or sent to browsers.

Steward user and announcement operations recheck current actor and target permissions in the final transaction. They do not expand owner exports. Failure-streak resets reuse the existing no-secret donation-review audit and its retention; read-only batch selection cursors store no job, selection or new user-associated table. Browser selections and privileged views are cleared on authority/session changes.

## The four checks

`legal_hold_steward_reads` records each steward's first/last authorized read and read count for a held donation or request log. The same transaction rechecks the current L6 role, reads the object and updates the audit. It grants no legal-hold administration or access to other held domains. Account deletion sets the actor to NULL; account exports exclude these management audits. Each rollup follows its parent hold and cascades when the hold metadata expires, 400 days after the hold ends. Administrator read audits retain their existing administrator-only identity rules. The two management roles see the same current donor and charity-caller identity, safe source and routed key identifiers; ordinary user and consumer projections remain owner-scoped and never reveal credentials.

`donation_handling` retains shared management state with its donation; processing actors are SET NULL on deletion and their identity is not copied. It is excluded from ordinary owner export. `charity_model_access` stores the current level mask and public plain-text description, cascades with its model and does not add caller records or export privileges.

`donation_quota_rules` and `donation_quota_epochs` hold current recurring settings and the minimum retired settings needed by accepted work. Export version 10 includes only each owned key's current `recurring_limits` RuleView from the same snapshot as the rest of the export. Steward access never expands that export scope. `donation_quota_receipts`, `donation_quota_periods`, `donation_quota_buckets` and `donation_quota_capacity` are internal and excluded. Buckets carry no caller, model, content or credential identity.

The recurring marker, receipt and terminal accounting transitions share the original claim transaction. Caller deletion releases unsent work and deidentifies dispatched work; donor deletion revokes new admission while existing sends settle the original key and rule generation. Neither path rewrites actual usage or transfers it to a new donation instance. Retired rules cannot be removed while their receipts or aggregates remain. Terminal donation retention first retires rules, then bounded quota cleanup releases aggregates and capacity, and only then removes the parent.

Completed sliding aggregates remain for at most 35 actual days; reset retains its current period and older periods still needed by unfinished receipts. A receipt's minimum completion evidence outlives those age limits until settlement. Each quota cleanup batch removes at most 1,000 rows; retirement shares a bounded mutation budget. Startup verifies receipt, aggregate, cache and capacity consistency before recovery and admission. Missing or inconsistent state fails closed and is not silently reset. These counters do not extend request-log or content retention.

For every table/column, answer all four. A missing answer is an acceptance gap.

1. **Export** — Include the owner's safe slice in the version 11 account export, or record
   an explicit policy exclusion. Never export secrets/ciphertext, CallerKey plaintext
   or verifier, report/device fingerprints, dispatch/idempotency/worker material,
   Debug bodies, device tokens, raw IP, raw upstream data, or another participant's
   identity/private result. Public game facts and terminal randomness proofs follow
   their explicit projections below; unrevealed seeds are always excluded.
   Amounts are canonical decimal strings; bounds fail closed rather than truncating.
2. **Delete** — Use the canonical cascade where it is sufficient. Where a reference
   must survive for settlement or audit, perform the prescribed final transaction and
   de-identify it. Any no-FK late write uses an atomic `INSERT ... SELECT ... WHERE
   EXISTS users` (or an equivalent conditional write), never read-then-write.
3. **Retention** — Apply the exact frozen deadline/cap below. All timestamps are
   server UTC seconds and `now >= deadline` is the boundary. Cleanup failure remains
   retryable and must not be reported as already deleted.
4. **Privacy** — The release zh/en text and every sink (JSON, CSV, HTML, log, error,
   header, and Debug projection) must match the safe projection. Bound and sanitize
   untrusted text for its sink. Configured secret fields are excluded from ordinary
   projections. Restricted original upstream failures are an explicit exception:
   echoed input or credentials may be retained under the policy below.

Runtime-only state is part of the same lifecycle boundary even when it has no table:
the shared per-account SSE ring is capped at 256 events, 512 KiB, and five minutes
(first limit wins), disconnect does not extend it, and an expired replay produces only
`gap` plus an authoritative snapshot. A Debug session is capped at ten idle minutes,
one absolute hour, 4 MiB / 32 traces / 128 events per account, and 64 sessions /
128 MiB globally; the Debug v2 ring additionally caps each session at 128 events,
each event at 512 KiB, and each session at two subscribers. L6 admin-safe client
state is cleared immediately on 401/403, demotion, ban, logout, or session replacement.

## New diagnostic, governance and activity families

The service does not actively persist request bodies or successful response bodies. The restricted original-error store can nevertheless contain upstream-echoed input, prompts or credentials. It captures HTTP-decoded entity/error-event bytes, with a 1 MiB event limit and explicit truncation, unavailable and capacity states. Ordinary retention is 30 days. The default 1 GiB payload budget is configurable from 1 MiB to 64 GiB, includes held bodies, and omits new bodies instead of evicting unexpired ones. It does not include SQLite or backup overhead. JSON/text/base64 views remain untrusted text/bytes and require current administrator or L6 session authority in the read transaction.

## Linearization and lifecycle acceptance

The deployed rc.3 `client-scans` behavior capped retained tasks at 32 and used one worker. Rc.4 retains that path for compatibility but uses the shared three-kind scan task machinery and the new 200-task/two-worker bounds above. Tasks remain private to their currently authorized creator. Source retirement, creator-account deletion and role loss clear both published and pending associations and identity-bearing checkpoints in the authoritative transaction, while coverage records that the frozen input changed. Original request-source retention remains authoritative; no prompt or request body is collected.

Image model discovery stores a bounded dispatch sidecar (`image_discovery_dispatches`) owned by the refresh operation: actual GET method/URL, empty request body/content type and dispatch time. It is written with the dispatch transition, survives later configuration edits, cascades with the refresh root and appears only through existing live diagnostic projections. It is excluded from personal exports and retains no Authorization headers or generation payload. Historical missing snapshots remain explicitly unavailable.

Account deletion and late callback/ACK/settlement writes must be linearized by one
single-writer transaction. If the late write wins, deletion cascades or explicitly
cleans it; if deletion wins, the conditional late write inserts zero rows. Neither
order may resurrect an account, wallet, identity, public rank, secret, or query
projection. Each owner must test both orders, replay, DB busy, crash/restart, and the
deadline boundary (`-1`, exact, `+1` second). The cross-domain lifecycle pass must also test 401/403, logout,
account-switch cache clearing, and export exclusion across every domain.

## Embedding request lifecycle

Embedding execution input is processed in bounded request memory and may appear in the owner's explicitly opened, bounded Debug memory trace. An upstream-echoed input can also occur in the restricted original-error store described above. Returned vectors are validated in bounded memory and are never persisted in the database, ordinary logs, alerts, exports, backups or Debug. Each upstream call receives a pseudonymous `user` scoped to the same user, deployment and canonical upstream origin; it is not persisted or added to diagnostics. Existing log retention, legal holds, anonymization, schema-12 export and account-retirement rules also cover `openai_embeddings` and `charity_embeddings`. No new content store, model-purpose field or background job is added. Registered game modules participate in the existing transactional export, deletion, retention and recovery sequence; schema 12 retains their earlier safe payment, asset and game-rule fields, Blackjack records and randomness proofs, loan receipts, reward holds, ranking facts and penalty history.

## Operator snapshot and destructive-fresh boundary

Complete operator snapshots are outside the account-export contract. They may contain
all private data, encrypted credentials, configuration, game state, and correlation
indexes, and must stay paired with the exact release, environment, master key, unit,
manifest, and checksums. Snapshot retention/deletion is operator-controlled and must
be disclosed by the instance policy; the service does not promise per-user erasure inside
historical snapshots.

Generation 2 accepts a fresh database only when main/WAL/SHM are all absent; an
existing 0-byte main, alpha.3/unknown generation, bad header/identity/manifest/secret
envelope/config, or an unsafe path fails closed. The Unreleased rc.5 source boundary is the exact rc.4 database at commit `8a46c72d911a914eabcb7ef17c537e7ac12d6969`, tree `cfb3b4bf2be82aca5b14336c8295491c4719ab87`; final target/source acceptance remains required. Historical rc.4 sources are identified below. The exact preceding deployed source at commit `4e06025c6bf23fbb0f34db96673b45ed01c42e97` (tree `6af9d8349d9049197366f29984e2e413090b7814`) is a separately verified compatibility case; other intermediate schemas are outside the guarantee. Existing economic facts, accounts, donations, model bindings, saved games, configuration and instance legal text are preserved. The role migration already present in that source is preserved, historical audit roles keep their meaning, and split Token counters never reconstruct old totals. ## Change discipline

Any new table, column, route, or retention value requires an explicit export
whitelist/exclusion, synchronous deletion and late-write behavior, an exact retention
sweep or cap, bilingual privacy review, and fixed-clock/cascade tests before release.

### Account deletion alerts and Discord blacklist

When a user deletes their account, a separate read-only security projection retains only known former site and Discord IDs, registration/deletion times, effective level, restriction and charity-pause state, source, pre-zero four-wallet amounts, donation credit and blacklist result. Older missing values remain null or `unknown`; they are never derived from another account using the same Discord ID. Administrators and current level-6 stewards can read authorized projections, but only administrators see deletion-alert references and minimal self-deletion duel-abort events. The latter are removed after 90 days; the deleted-account projection has no automatic expiry. Neither is in a personal export. The existing administrator-only economic deletion alert remains a separate record: negative general or game credit keeps it unresolved unless automatic blacklisting succeeds, which resolves it in the same transaction; other deletion alerts start resolved. Resolution does not erase its retained audit facts.

The snapshot and account retirement share one transaction after required domain handoffs and before wallet zeroing. Same-Discord minimum already-used reward/once-only qualifications and unexpired violation or frequency windows can remain enforceable across re-registration; they do not restore progress, resources, manual role or old private records. Self-deletion under an effective ban, charity pause or negative general/game balance adds a blacklist reason event. The first reason, actor and creation time remain immutable; later reasons append, and the entry lasts until an administrator removes it. Administrators and current level-6 stewards may add entries within their different authority limits; only administrators remove them. Registration and ban mutations recheck the identity in their transaction. Removing a blacklist entry does not unban an account or restore its credentials.
