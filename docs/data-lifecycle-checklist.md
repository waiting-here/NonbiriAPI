# Data Lifecycle Checklist (Generation 2 export / delete / retention / privacy)

> Status: **v1.0.6 contract** — this checklist describes the
> release's export, deletion, retention, and privacy boundary. Source publication does
> not itself upgrade an instance; deployment status is specific to each operator.
>
> Canonical DDL: `internal/db/generation_two.sql`, embedded by `internal/db/schema.go`, plus registered extension schemas; manifest: `internal/db/schema_manifest.go`;
> target fingerprint: the build’s canonical `GenerationTwoSchemaHash` and complete manifest.

The table cells below describe the version contract for each exact Generation 2 table
family. The registered routes, export builder, deletion coordinator, retention workers,
and bilingual privacy text are covered by their implementation and contract tests.
Schema presence alone never creates a route or expands a response.

Current account export format 23 includes safe `gacha` balances, owned cards, guarantees, claims, activity journals, draw details within 180 days and the saved appearance artwork key. Its filename is `nonbiriapi-account-export-v23.json`; SQLite `user_version` remains 2 and the current storage schema is 26. All rows below describe current retained fields. This does not assert that a particular instance has been upgraded.

`channel_charity_binding_presets` and `channel_charity_binding_mappings` contain
shared channel configuration without donor or operator identity. They are excluded
from personal exports and retained with the channel. Removing a charity target
leaves its preset reference visible to authorized managers for repair; applying
the preset skips that missing target. Mutations and batch results use existing
role-scoped control receipts and retention. No additional personal audit history
is created.

Optional deployment routes send selected upstream requests, provider credentials
and responses through Cloudflare AI Gateway. The gateway token is deployment
configuration, excluded from database records, exports and diagnostics. Routed
responses are checked for known credential reflections before header and error
capture; direct responses retain the existing diagnostic contract. Gateway logging,
cache, extra retries and billing fallback are disabled for these routes. Operators
must disclose the intermediary and maintain its settings; these controls do not
guarantee end-to-end zero retention.

`account_mfa_credentials` holds purpose-encrypted authenticator seeds and the
last consumed time step. `account_mfa_pending` holds a ten-minute enrollment
bound to a browser session; bounded session retention removes expired setup.
`account_mfa_attempts` keeps one failed-code budget per account across session
replacement and process restarts. `account_mfa_proofs` grants at most seven days
for a specific session and credential generation. All four are excluded from
account exports and cascade on account deletion. Session removal cascades pending
setup and proofs; removing enrollment removes its proofs. Administrator reset
also removes all target browser sessions, retaining CallerKey credentials and
the failed-code budget. Seeds, codes and QR payloads never enter logs or audit
messages; offline credential verification checks the encrypted MFA material.

Donated keys include the current U128 failure-disable threshold in owner, management and safe export projections. It follows the parent key/donation lifecycle and adds no retention window. Policy edits add no-secret donation review facts, retained under the existing donation-review policy; account deletion removes actor links. A zero threshold preserves error counting but never disables a key for errors. Expiry, withdrawal, bans, manual switches and quota limits remain effective.

Gateway v3 adds a default-off site setting for cost attribution. The optional pseudonym is computed per user and final gateway origin from the deployment key and is never stored as a new identity table, exported, or shown in diagnostics. Debug records only whether it was sent. The receiving gateway can link requests in that scope; ordinary request content and provider retention retain their existing boundaries. Gateway model controls are administrator-managed database configuration. Updates preserve existing credentials, counters, generations, error-disablement and configured legal overrides. Explicit store control rejects by default; a verified OpenAI profile forwards it, while administrator-enabled `omit_false` deliberately omits the control. Neither policy guarantees zero retention across upstream intermediaries.

Credit history, ledger exports and administrator transaction detail expose only the
last 30 days of operations. Six-hour maintenance compacts older entries into per-account
opening balances and the existing non-personal hour/day audit totals. It deletes expired
entries and unreferenced operations. Pending settlement and legal holds retain the full
required evidence until resolved; existing domain references retain only minimal
idempotency receipts without ledger amounts, actors or reasons. These receipts are not
exposed as history. Opening balances cascade with account deletion. SQLite reuses freed
pages; maintenance does not make another database copy or run a full VACUUM. Request
links follow their own owner-scoped 30-day window and never expose another caller.
Older audit ranges use complete site-hour boundaries, reported in response metadata.

Authenticated pre-handler rejections and short charity rejections use the same 30-day owner-scoped request-log policy. Pre-handler rows identify the phase and safe rejection stage/reason, with no attempts, usage or call fee; an independently authorized penalty has its own ledger entry. Durable violation windows contain bounded event times, kinds and request references, survive restart without repeating an already executed measure, and are pruned by logical window expiry. They contain no request bodies and are excluded from export. Account deletion clears account-owned windows and caches while preserving unexpired same-identity continuity facts until their original deadline.

Every user-associated table or column MUST be checked in the same task that introduces
it. This includes direct `users(id)` links, transitive foreign keys, and no-FK user
references used for late-callback suppression.

`users.discord_gate_policy` stores the administrator's current registered-user sign-in choice (`inherit`, `require`, or `exempt`). Personal account exports include it; account deletion removes it with the user, and re-registration starts with `inherit`. Configuration/profile mutations use the existing control-mutation receipts and retention. The setting creates no extra identity history or Discord token storage. Login checks the current policy and live account inside the session transaction; it cannot recreate a deleted account or issue a session during deletion.

`dispatch_response_starts` records a claim's consumption checkpoint. For an actual upstream HTTP 200 stream this begins at response acceptance, including empty or subsequently failed streams; it does not assert protocol completion. It stores no content, credentials or independent user identity and is excluded from account export. Existing usage and credit records contain the safe economic result. The checkpoint follows the parent claim's retention and cascades on claim deletion. Deidentified settlement handoff prevents late completion from recreating deleted user data.

`endpoint_key_limits` stores the shared physical key concurrency and RPM values selected by its owner or an authorized donation manager. Management edits compare both donation and physical-key revisions and audit safe old/new values. The owner resource export includes both; the endpoint-key foreign key cascades their deletion with the key/account. They have the same lifetime as the resource. Administrator/steward views disclose and edit only the resources already authorized for those views; L5 remains within its existing model/source scope. These shared limits also affect personal use. Deleted donation source keys show no current configuration. Admission reuses existing dispatch metadata and adds no counters, request content, retention period or late-writing worker. Recovery and request/account deletion continue through the existing claim state machine; in-flight donor keys and their secret retention rules are unchanged.

General, game, draft-paper and brush accounts are conserved independently. General/game balances may be signed; activity currencies are whole units and never become game-payment funds. `credit_entries.asset_type` survives account-reference removal. The export includes the requester's safe balances, payment splits, activity exchanges and original-asset history. Deletion releases pending capacity and clears all four user wallets atomically against their own asset's external account. General-only charity fees may exceed the admitted reserve when actual usage is known; settled historical charges are never repriced. Administrator user adjustments remain restricted to the existing general/game or cumulative-donation targets.

`game_checkins` stores the independent daily game award and follows the account's lifetime, export and cascade deletion. `game_onboarding_completions` stores game/task key, award, operation and completion time; each of 22 tasks is unique per account, survives 30-day game cleanup and is exported/deleted with that account. `game_onboarding_holds` reserves reward capacity until the parent game's terminal transaction releases it; it cannot silently cascade and lose capacity. The export includes only each hold's ID, game/task key and creation time, excluding internal amounts and parent references.

Saved game rows include rules version and original payment sources. Fishing adds frozen cut rates and gross/net values; LinkLink adds hint/refresh counters and reads six leaderboards from retained successful version-2 summaries. RPS exports only the viewer's source balances and nullable recorded original buy-in/cash-out fields. Old unrecorded values remain null. These additions inherit their parent retention and synchronous deletion rules. The private stable LinkLink tie key follows account lifetime and is never exported or sent to browsers.

Steward user and announcement operations recheck current actor and target permissions in the final transaction. They do not expand owner exports. Failure-streak resets reuse the existing no-secret donation-review audit and its retention; read-only batch selection cursors store no job, selection or new user-associated table. Browser selections and privileged views are cleared on authority/session changes.

Gemini, Responses and Decisions reuse existing endpoint, credential, request and accounting records, including their owner export, deletion and retention. Translated Chat continuations carry Google thought signatures or OpenAI encrypted reasoning through the client; they are not stored as server sessions. Successful response content remains transient. Responses explicitly sends `store:false`; provider retention still follows its own policy.

## The four checks

`legal_hold_steward_reads` records each steward's first/last authorized read and read count for a held donation or request log. The same transaction rechecks the current L6 role, reads the object and updates the audit. It grants no legal-hold administration or access to other held domains. Account deletion sets the actor to NULL; account exports exclude these management audits. Each rollup follows its parent hold and cascades when the hold metadata expires, 400 days after the hold ends. Administrator read audits retain their existing administrator-only identity rules. The two management roles see the same current donor and charity-caller identity, safe source and routed key identifiers; ordinary user and consumer projections remain owner-scoped and never reveal credentials.

`donation_handling` retains shared management state with its donation; processing actors are SET NULL on deletion and their identity is not copied. It is excluded from ordinary owner export. `charity_model_access` stores the current level mask and public plain-text description, cascades with its model and does not add caller records or export privileges.

`donation_quota_rules` and `donation_quota_epochs` hold current recurring settings and the minimum retired settings needed by accepted work. The export includes only each owned key's current `recurring_limits` RuleView from the same snapshot as the rest of the export. Steward access never expands that export scope. `donation_quota_receipts`, `donation_quota_periods`, `donation_quota_buckets` and `donation_quota_capacity` are internal and excluded. Buckets carry no caller, model, content or credential identity.

The recurring marker, receipt and terminal accounting transitions share the original claim transaction. Caller deletion releases unsent work and deidentifies dispatched work; donor deletion revokes new admission while existing sends settle the original key and rule generation. Neither path rewrites actual usage or transfers it to a new donation instance. Retired rules cannot be removed while their receipts or aggregates remain. Terminal donation retention first retires rules, then bounded quota cleanup releases aggregates and capacity, and only then removes the parent.

Completed sliding aggregates remain for at most 35 actual days; reset retains its current period and older periods still needed by unfinished receipts. A receipt's minimum completion evidence outlives those age limits until settlement. Each quota cleanup batch removes at most 1,000 rows; retirement shares a bounded mutation budget. Startup verifies receipt, aggregate, cache and capacity consistency before recovery and admission. Missing or inconsistent state fails closed and is not silently reset. These counters do not extend request-log or content retention.

For every table/column, answer all four. A missing answer is an acceptance gap.

1. **Export** — Include the owner's safe slice in the version 20 account export, or record
   an explicit policy exclusion. Never export secrets/ciphertext, CallerKey plaintext
   or verifier, report/device fingerprints, dispatch/idempotency/worker material,
   Debug bodies, device tokens, raw IP, raw upstream data, or another participant's
   identity/private result. Public game facts and terminal randomness proofs follow
   their explicit projections below; unrevealed seeds are always excluded.
   Amounts are canonical decimal strings; bounds fail closed rather than truncating.
2. **Delete** — Use the canonical cascade where it is sufficient. Where a reference
   must survive for settlement or audit, perform the prescribed final transaction and
   de-identify it. Any no-FK late write uses an atomic `INSERT ... SELECT ... WHERE
   EXISTS users` (or an equivalent conditional write), never read-then-write.
3. **Retention** — Apply the exact frozen deadline/cap below. All timestamps are
   server UTC seconds and `now >= deadline` is the boundary. Cleanup failure remains
   retryable and must not be reported as already deleted.
4. **Privacy** — The release zh/en text and every sink (JSON, CSV, HTML, log, error,
   header, and Debug projection) must match the safe projection. Bound and sanitize
   untrusted text for its sink. Configured secret fields are excluded from ordinary
   projections. Restricted original upstream failures are an explicit exception:
   echoed input or credentials may be retained under the policy below.

Runtime-only state is part of the same lifecycle boundary even when it has no table:
the shared per-account SSE ring is capped at 256 events, 512 KiB, and five minutes
(first limit wins), disconnect does not extend it, and an expired replay produces only
`gap` plus an authoritative snapshot. A Debug session is capped at ten idle minutes,
one absolute hour, 4 MiB / 32 traces / 128 events per account, and 64 sessions /
128 MiB globally; the Debug v2 ring additionally caps each session at 128 events,
each event at 512 KiB, and each session at two subscribers. L6 admin-safe client
state is cleared immediately on 401/403, demotion, ban, logout, or session replacement.

## New diagnostic, governance and activity families

The service does not actively persist request bodies or successful response bodies. The restricted original-error store can nevertheless contain upstream-echoed input, prompts or credentials. It captures HTTP-decoded entity/error-event bytes, with a 1 MiB event limit and explicit truncation, unavailable and capacity states. Ordinary retention is 30 days. The default 1 GiB payload budget is configurable from 1 MiB to 64 GiB, includes held bodies, and omits new bodies instead of evicting unexpired ones. It does not include SQLite or backup overhead. JSON/text/base64 views remain untrusted text/bytes and require current administrator or L5/L6 session authority in the read transaction. Authorized administrator and L6 log views and downloads preserve complete saved text and bytes, including IP addresses; L5 upstream error payloads and error-text projections replace IPv4 with `[redacted]`, including decoded binary payloads before base64 encoding, copying and downloading. Source IPs, endpoint addresses, IPv6 and stored originals remain unchanged; capture byte counts still describe the original. Ordinary user display protection remains. This does not expand collection, retention or the fields a role may access. Editable endpoint/IP-rule values and normal model output retain their values.

## Linearization and lifecycle acceptance

Risk scan tasks use the shared 200-task/two-worker bounds above and remain private to their currently authorized creator. Source retirement, creator-account deletion and role loss clear published/pending associations and identity-bearing checkpoints in the authoritative transaction; coverage records that the frozen input changed. Original request-source retention remains authoritative; no prompt or request body is collected.

Image model discovery stores a bounded dispatch sidecar (`image_discovery_dispatches`) owned by the refresh operation: actual GET method/URL, empty request body/content type and dispatch time. Account deletion and late callback/ACK/settlement writes must be linearized by one

deadline boundary (`-1`, exact, `+1` second). The cross-domain lifecycle pass must also test 401/403, logout,
account-switch cache clearing, and export exclusion across every domain.

## Operator snapshot and destructive-fresh boundary

Complete operator snapshots are outside the account-export contract. They may contain
all private data, encrypted credentials, configuration, game state, and correlation
indexes, and must stay paired with the exact release, environment, master key, unit,
manifest, and checksums. Snapshot retention/deletion is operator-controlled and must
be disclosed by the instance policy; the service does not promise per-user erasure inside
historical snapshots.

Normal v1.0.6 startup accepts fresh storage or current schema 26; exact schema 16–25 structures use the independent converter. Unknown or partial sources are rejected before writes. Fresh creation requires the main database and sidecars to be absent. Conversion preserves accounts, economic facts, credentials, saved games, configuration and instance legal text. Full historical audits use offline `maintenance verify`. The [database upgrade guide](database-upgrades.md) identifies the exact source and restore requirements.

Starting fresh from an unsupported version uses a separate empty path and resets active application state. A complete old recovery set remains sensitive until its retention purpose ends. Never combine an old binary with a newer database or restore a stale snapshot over newly accepted data automatically.

Reactivating an old snapshot requires disclosure of its data cutoff and repeating any needed revocation or configuration changes. Account deletion does not erase historical operator snapshots.

## Change discipline

Any new table, column, route, or retention value requires an explicit export
whitelist/exclusion, synchronous deletion and late-write behavior, an exact retention
sweep or cap, bilingual privacy review, and fixed-clock/cascade tests before release.

### Account deletion alerts and Discord blacklist

When a user deletes their account, a separate read-only security projection retains only known former site and Discord IDs, registration/deletion times, effective level, restriction and charity-pause state, source, pre-zero four-wallet amounts, donation credit and blacklist result. The existing administrator-only economic deletion alert remains a separate record: negative general or game credit keeps it unresolved unless automatic blacklisting succeeds, which resolves it in the same transaction; other deletion alerts start resolved. Resolution does not erase its retained audit facts.

The snapshot and account retirement share one transaction after required domain handoffs and before wallet zeroing. Same-Discord minimum already-used reward/once-only qualifications and unexpired violation or frequency windows can remain enforceable across re-registration; they do not restore progress, resources, manual role or old private records. Self-deletion under an effective ban, charity pause or negative general/game balance adds a blacklist reason event. The first reason, actor and creation time remain immutable; later reasons append, and the entry lasts until an administrator removes it. Administrators and current level-6 stewards may add entries within their different authority limits; only administrators remove them. Registration and ban mutations recheck the identity in their transaction. Removing a blacklist entry does not unban an account or restore its credentials.

`charity_header_sessions` and `charity_header_uses` hold temporary upstream correlation values, excluded from account-content exports, public configuration and logs. Charity consumption remains in its existing aggregate. User/model deletion cascades both tables; completion updates only surviving matching values and cannot recreate deleted data.

Startup recovery releases unfinished uses. These values are never authentication credentials. Configuration uses existing model-management authority. ## Rewards and redemption protection

Redemption protection reuses `abuse_windows/events`, cases, actions and safe penalty history with kind `redemption_code`. Unknown/malformed and already-claimed submissions count directly. A first business refusal for an existing code stores only a bounded grace fact keyed by identity and campaign; it contains no submitted code. Grace and violation windows expire under their configured rolling-window policy and survive restart and same-identity re-registration without restoring deleted account data.

The `reward_redemption` idempotency scope retains a safe outcome and keyed request digest for at least 24 hours and the initial effective violation window. It follows existing account deletion and bounded receipt cleanup, is excluded from export, and prevents retries from increasing the count. Automatic-ban evidence records the rule snapshot, counts and times without code text; ended cases follow the existing 90-day policy.

Reward receipts are included in current account exports under `rewards`. They contain the account’s successful site-wide and code rewards, quantities, duplicate conversions and skipped items, without code text, eligibility configuration, other recipients or retry hashes. Receipts remain for the account lifetime and are removed on deletion; campaign totals and used quota remain. See [rewards](rewards.md).
